# D3 repair11 runner path and review boundary

This is a prepared future continuation path, not an executed resource run. `runner.py` requires `--authorized-reuse` plus a bounded `--total-seconds`; the flag records a future orchestration decision and is not technical proof of that decision. The real resource gate remains closed pending original TASK-084 incremental review and separate resource authorization. No Docker, PG or Windows Job was started by repair11.

1. The runner snapshots its own code, `controlled_child.py`, `contracts.py`, and each fixture attempt into unique directories with SHA-256. It projects Docker inspect fields through `--format` so `Config.Env` and the old password never enter runner output. It requires the full CID, exact labels/image/volume/network/limits, stopped state, free loopback port, and no other active task-083 container. It never creates a container.
2. After a separately authorized exact-CID start, it tries only local Unix-socket authentication as database role `task083_d3` using container OS user `postgres`. This route and self-password-change privilege are **unproven**. Failure leads to exact-CID stop. If available, the same runner generates a new random hex secret in memory, sends `ALTER ROLE` only via `docker exec -i` stdin, and checks loopback database/user/internal-port with the new credential. It does not read old Env/secret, disable authentication, create another role, or write DSN/secret to evidence.
3. Each selected attempt starts one Python fixture suspended. The test-only `ControlledChild` creates an unnamed outer Windows Job with `KILL_ON_JOB_CLOSE`, captures a process handle/PID/creation time, assigns that suspended process to the outer Job, queries active count, then calls `ResumeThread`. The controller never opens or holds the named business Job. Create/identity/Assign failure uses the exact suspended process handle for termination before any Resume; assigned failures terminate the outer Job and require `ActiveProcesses==0`. Closing the last outer handle on runner death kills assigned descendants by OS rule. A crash between suspended creation and assignment could leave an inert suspended child; no SUP/worker can start from it, but cleanup of that pre-assignment crash is not evidenced and must be treated as unknown. Actual nested Job behavior still needs real review/run evidence.
4. Anonymous output pipes feed memory; stdout/stderr are written separately after a secret scan/redaction. Every attempt has independent as-run bytes/hash, output, exit and meta. The result contract requires exactly one start/result for every selected scenario in order, one final complete with exact parts and `all_pass=true`, child exit 0, no timeout, outer tree zero and control handles closed. Any missing/duplicate/unknown/partial result fails. Failure and cleanup error are separate. A nonzero verdict exits 1. A follow-up attempt is allowed only after a failed PG-only path whose outer tree is proven zero; a started Windows scene or cleanup uncertainty stops the run.
5. A single monotonic total deadline bounds Docker/auth/attempts. Each attempt has a 600-second batch bound with 60 seconds reserved, one fixture command has a 60-second bound including five seconds for its cleanup, and every `scenario_start` creates an active 30-second stop deadline. The earliest deadline governs waits and cleanup; exhausted deadlines never receive a fresh one-second wait. The child has `PYTHONOPTIMIZE=0`, `-B`, and a runtime `sys.flags.optimize` check. Exact-CID stop/kill/inspect shares the remaining total deadline and a 60-second cleanup window. If identity or stopped state cannot be proved, `cleanup_incomplete` remains true and success is impossible.
