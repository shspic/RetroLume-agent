# 03 必要的技术可行性验证

你是 Astra 或实验执行者。遵守 `docu/AGENTS.MD`，由 Astra 按 `docu/WORK.MD` 给实验/测试建卡并指定档位。先读关联 REQUIREMENTS、调研 HYP、已有证据、环境与授权。

先回答：哪个未经证实的问题会改变现在的关键决定？为什么不能用现有证据或正常开发验证？若没有，不运行实验、不创建假报告，在执行文档的流程配置/调研写“无需单独验证及重启条件”后继续。材料不足可做明确标记的前置临时验证，不能冒充正式可行性结论。

确需实验时：

1. 沿用 HYP；为单一问题建 SPIKE 和 TASK，写最小范围、排除项、相关需求、版本/环境、安全数据、成功/失败标准、观测方法、投入上限、停止条件及替代方案。通常先做一个最重要假设，剩余保留队列。
2. 将实验放 `Ndocu/spikes/SPIKE-XXX/`，保留最小说明、代码/配置和脱敏证据。不得写正式业务模块、用生产数据试验或把实验直接当生产实现；安装、账号、费用等按已有授权核对，不重复确认。
3. 只选与 HYP 直接相关的类型：开源适配看核心能力/接口/依赖；外部 API 看必需调用/认证/失败/配额和费用；AI/RAG/Agent 看代表样本、基线、质量/引用/工具调用及错误恢复；性能看环境/规模/并发/方法；迁移看副本完整性/幂等/恢复；兼容看目标平台运行。只测足以支持决定的部分，不机械扫完整清单；Mock 和小样本注明外推限制。
4. 记录实际步骤、版本、结果、警告、原始错误和证据。达到判定或投入上限即停；两次有依据的修正仍失败交回 Astra。不把缺环境判成技术不成立，不通过改指标“做成功”。
5. HYP 结论只能为成立、部分成立、不成立、无法验证、需要更多证据；记录适用边界和需求影响。结果涉及高影响安全/数据/核心结构等时按 WORK 判定审计，已要求的独立审计未完成仍保留相关阻塞。

Astra 形成 `docu/TECHNICAL_FEASIBILITY.MD`：完整HYP与本批选择、SPIKE/任务、方法与证据、结论限制、替代方向、需求影响、审计/遗留及下一步，并同步 CHANGE/索引/状态。实验失败可进入调整方案，未验证部分不能宣称可行；不影响它的需求、架构、计划草案继续交付，受影响关键承诺不生效。
