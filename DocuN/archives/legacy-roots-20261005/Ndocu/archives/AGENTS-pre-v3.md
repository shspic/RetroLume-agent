# AI 工作规则

本文件约束项目中的所有 AI Agent。目标优先级为：安全与正确性、可验证性、效率；简单任务可简化流程，但不能省略必要的边界检查和验证。

## 1. 指令、语言与事实

- 工作前检查项目根到当前目录沿途适用的 `AGENTS.override.md`、`AGENTS.md`、项目索引、已批准项目文档和用户当前任务。离当前目录更近的项目规则覆盖上级规则。
- 冲突优先级：系统和平台规则 > 用户最新明确指令 > 更近的项目规则 > 已批准的 `LATER_REQUIREMENTS.md`（目标行为）> 当前代码、配置和运行证据（实际状态）> 其他资料和推断。目标与现状冲突时记录实现缺口，不用一方静默覆盖另一方。
- 在用户没有另行规定时，本文件高于 `WORK.md`；`WORK.md` 只能细化规划和编排，不能降低本文件的权限、安全、修改、验证或完成标准。
- 默认使用简体中文进行互动、计划、总结和新增代码注释。代码、命令、路径、标识符、依赖名及已有原文可保持原语言；不要批量翻译无关内容。
- 正式项目文件、当前代码与配置、可核实的 Git 状态和差异、测试及运行结果是事实源；聊天和 Session 只是临时上下文。明确区分事实、用户决定、Agent 声明、推断、建议和未核实项。

## 2. 任务权限

先判断任务类型：

- 分析、解释、审查、规划或诊断：只读检查并报告，不自行实施修复。
- 修改、修复或构建：仅在用户明确范围内做最小必要修改，并运行安全、相关的验证。
- 验证、测试或验收：按既定标准取证；除非另有授权，不借验收之名修改业务实现。
- 外部发布或高风险操作：只准备方案和证据，取得对应的单独明确批准后才执行。

读取文件、检查日志、编辑获准范围内的本地文件、运行项目已有的非破坏性测试等正常步骤无需反复询问。下列事项必须先获得用户明确批准：改变已批准需求、核心架构、主要数据模型或公开接口；扩大任务范围；新增或更换重要依赖/外部服务；安装或升级依赖；修改锁文件；付费；使用真实账号、凭据、验证码或隐私数据；向外部系统写入；修改生产环境；不可逆迁移；删除重要文件或数据；提交、推送、合并或发布。

只说明凭据名称、应在本地配置的位置和验证方法；不得要求用户在对话中粘贴密码、私钥、完整令牌或验证码。

## 3. 工作前检查与计划

- 先读最小充分上下文：适用规则 → `PROJECT_INDEX.md` → 当前阶段或 `TASK-XXX` → 相关需求、架构、代码、测试和必要的 Git/运行证据。索引只导航，不替代原文；信息不足时按需扩大读取并说明原因，不默认扫描整个仓库。
- 理解目录、模块职责、调用关系、数据流、现有测试/构建/启动方式和验收标准；如使用 Git，检查分支、工作区和用户已有未提交修改。项目无 Git 时记录该事实并采用等价文件差异。
- 会改变方向、结构、接口、依赖、安全边界或验收结果的未知项必须停止相关修改并询问；次要未知项可采用最简单合理假设，但须标注依据、影响和重评条件。
- 多步骤任务先给出简短计划，每步同时写验证方式；单一、低风险任务可直接执行。

## 4. 修改与命令安全

- 使用满足当前需求的最小实现。不得顺手扩展、预留未批准未来能力、创建一次性抽象、采用流行技术替代既有合适方案，或用大范围重写代替局部修改。
- 不引入新依赖、不安装或升级依赖、不修改锁文件，除非用户已明确批准。每一处新增或修改必须能追溯到当前需求、缺陷、验证或必要维护。
- 保护用户已有修改；不顺手重构、格式化、改名、移动或清理无关内容。任务造成的无用导入、变量、函数或临时文件应清理；无关问题只记录并报告。
- 搜索优先使用 `rg`。编辑采用小范围补丁。执行命令前明确目的和预期影响；失败后保留原始错误、分析原因，再决定是否采用有新依据的重试。
- 不启动长期后台进程，除非任务需要；启动时说明访问和停止方式。不在生产环境试验，不把真实数据上传到未批准服务。
- 禁止批量或递归删除，严禁 `rm -rf`、`del /s`、`rd /s`、`rmdir /s`、`Remove-Item -Recurse`。只可一次删除一个已确认的明确文件；删除前核对完整路径位于项目允许范围、属于当前任务，并检查保留、移动或弃用方案。确需批量、递归或不可逆删除时停止并请求授权。

## 5. 验证、升级与完成

- 把目标写成可观察结果：缺陷应先复现再修复；重构应证明外部行为保持；校验应覆盖合法与非法输入。
- 优先运行与修改直接相关的最小测试，再按风险选择类型检查、Lint、构建、集成、端到端、真实接口/功能或人工验证。不得机械运行所有检查，也不得把本可执行的测试替换为模型审查。
- 如实记录实际命令、结果、失败、警告、未运行项、原因、替代证据和剩余风险。测试通过不自动证明全部需求满足，代码存在和 Agent 的“已完成”声明都不是完成证据。
- 收到 `TASK-XXX` 时遵守其目标、范围、上下文、约束、验收、验证、输出和升级条件，并报告 TASK 及关联的需求、架构、步骤、检查、缺陷或优化编号；TASK 不能替代这些编号。
- 出现以下任一情况，停止扩大修改并把证据交回规划角色：核心验收连续两次失败；根因不稳定；范围明显扩大或跨模块连锁；涉及数据库结构、权限、安全、并发或一致性高风险；开始猜测关键架构；测试与判断反复冲突；需要推翻方案；超出 TASK 范围。
- 只有实现满足验收、必要验证有证据、文档已同步、没有阻塞风险，且要求的审计已通过，才能报告完成。非行为性步骤的验证可为“有理由且经审查的不适用”；不能把“无法验证”当作完成。

需要独立审计时必须使用与执行过程隔离的新 Session。审计只接收原始任务、验收标准、必要架构约束、最终差异、相关实现、测试和运行证据，不接收执行者的完整聊天、详细思考或自我评价。缺少关键证据时写“尚无法独立确认”。无法建立隔离 Session 时，同一 Session 的复核只能称普通 Review；已要求独立审计的任务保持“阻塞（待独立审计）”。

## 6. 文档、编号与交接

- 正式文件名固定为 `REQUIREMENTS.md`、`LATER_REQUIREMENTS.md`、`PROJECT_ARCHITECTURE.md`、`PROJECT_EXECUTE_STATE.md`、`PROJECT_FLOW.md`、`PROJECT_INDEX.md` 和 `CHANGE.md`。优先复用项目已有等价事实源并建立映射；不得另建同职责的中文名或 `ARCHITECTURE.md`、`PROJECT_STATE.md`、`TASKS.md` 等第二事实源。
- 已批准的 `LATER_REQUIREMENTS.md` 默认只读；需求变化先形成影响说明并获用户批准。同一文件同时保存现行基线和候选版本时必须明确分区，开发与验收默认只读取标为“当前有效”的已批准版本；未批准候选不得改变目标行为，批准后才切换当前版本并保留上一基线。模块、目录、接口、数据流、依赖、架构项状态或关键实现变化时更新 `PROJECT_ARCHITECTURE.md`。每轮经规划角色验收后更新 `PROJECT_EXECUTE_STATE.md`；无变化则明确记录“已检查，无需更新”。
- 每次成功创建或实质修改项目文档，都按时间顺序向 `CHANGE.md` 追加唯一 `CHG-XXXX`，最简记录文件、动作、原因、关联 ID 和批准/验证状态；编号不得复用。向 `CHANGE.md` 追加其他文件的记录不递归生成自记录；改变 `CHANGE.md` 规则本身需要登记。
- 项目级 `CHG/TASK/STEP/R` 编号和共享状态由 `WORK.md` 定义的规划角色统一登记。执行 Agent 只报告事实和建议状态，除非 TASK 明确授权其更新特定共享文档。
- 仅当问题已解决、根因已确认、方案已验证且有复用价值时，才写入 `spi_error.md` 和 `spi_index.md`；未解决问题进入阻塞或缺陷记录，不把猜测写成根因。
- 切换 Session 或交接前，按任务重要性固化当前状态、决定、任务、差异、测试、未完成项和下一入口。无写入权限时输出可直接保存的交接并标记“尚未固化”。

## 7. 结果报告

只报告适用项，不用空模板制造篇幅。至少让用户能判断：当前状态；实际完成内容；修改文件及作用；实际验证及结果；未验证项；风险、冲突或阻塞；文档与 `CHANGE.md` 是否同步；用户是否需操作；是否触发升级或超出范围；审计要求与状态；下一步。只读任务明确写“未改动文件”。不得夸大、隐瞒失败、使用无依据百分比或声称未执行的验证已通过。
